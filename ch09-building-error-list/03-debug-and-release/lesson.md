# Debug and Release configurations

A configuration is a named set of build settings. Visual Studio has two that you will see on the toolbar: Debug and Release. The configuration dropdown shows which one is active, and the next build uses it. The same code compiles to different output depending on the configuration, so it matters which one you choose.

## Debug and Release at a glance

| Feature | Debug configuration | Release configuration |
|---|---|---|
| Primary goal | Writing, testing, and stepping through code. | Deploying the final app to users or production. |
| Code optimization | Disabled. Code runs line by line, as written. | Enabled. The compiler and runtime simplify the code, and the JIT compiler may inline small methods. |
| Debug symbols (.pdb) | Generated in full, so breakpoints and variable inspection work reliably. | Generated by default too, so crash dumps can be read. It can be set to produce none. |
| Preprocessor constants | Defines DEBUG and TRACE. | Defines TRACE only. Blocks wrapped in #if DEBUG are removed. |
| Performance and size | Slower execution, and larger output because of the extra information. | Faster execution, and smaller output. |
| Output folder | bin\Debug\net10.0\ for this project. | bin\Release\net10.0\ for this project. |

The output folder includes the target framework, net10.0 here. The folder names may differ in another project, so check the Output window to see the exact path.

## Debug

Debug is the default. It keeps the information the debugger needs, so you can pause the program, step through a line at a time, and read the values of variables. Chapter 10 covers those steps. The trade-off is speed. Debug runs more slowly, because the code is not optimized, and the output is larger.

## Release

Release is for the version you hand to other people. The compiler and the runtime simplify the code, so the program runs faster and uses less memory. The debugger can still attach to a Release build, but the code it shows may not line up with the source line by line, because the optimizer has moved things around. Use Debug when you need to step through the code, and Release when you need to know how the program behaves when it ships.

## Code that changes with the configuration

The DEBUG symbol lets you write code that only runs in a Debug build. Debug.Assert also depends on DEBUG, so it does nothing in a Release build.

```csharp
using System.Diagnostics;

#if DEBUG
Console.WriteLine($"Prices received: {prices.Count}");
#endif

Debug.Assert(prices.Count > 0, "The list should not be empty.");
```

The first line prints only in a Debug build. The Debug.Assert line shows a message in a Debug build when the list is empty, and it does nothing in a Release build. Use these for checks that help while you develop, and keep anything a user depends on outside them.

## Try it

1. Look at the configuration dropdown on the toolbar. It should read Debug.
2. Press {{Ctrl+Shift+B}}. Find the output path in the Output window, and check that it ends in bin\Debug\net10.0\.
3. Open the dropdown, and choose Release. Press {{Ctrl+Shift+B}} again.
4. Find the new output path, and check that it ends in bin\Release\net10.0\.
5. Open both folders in File Explorer, and compare the size of the PriceReport output in each. The Release copy is usually the smaller one.
6. Change the dropdown back to Debug.

## Common mistake

A program can behave differently in Release than in Debug, because the optimizer changes the order of the work it does. Test the Release build before you hand it to anyone, and do not rely on a Debug run alone.
